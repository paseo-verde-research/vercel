MyBatis vs. jOOQ vs. Jdbi: Java Persistence on 256 MB RAM

by Ted Kupolov · October 14, 2026

All three applications completed the workload, with median Java RSS around 111–113 MiB. Their paging, package sizes, and application responsibilities differed.

Why compare SQL-first persistence libraries?

The earlier Javalin and Spring Boot experiment used raw JDBC to keep database work explicit. For an application I would maintain, I also wanted to compare libraries that take over some of that work.

This experiment records runtime, package, and application-code measurements for Jdbi Core, MyBatis Core, and jOOQ Open Source Edition in the same Javalin application on a 256 MiB server. It describes the implementation responsibilities and observed resource use of explicit SQL APIs and a type-safe SQL DSL, using conventional HotSpot and minimal infrastructure.

Shared application and setup

All three variants use the same plain Java repository contract and domain records, constructor-injected controller, explicit application wiring, H2 file database, HikariCP pool, StatLite monitoring, JVM flags, routes, fixture, SQL semantics, and workload. The controller remains independent of each persistence library. Each implementation uses explicit repository construction and keeps framework-specific failures inside its persistence layer, while using idiomatic internals for its library.

The common 256 MiB experiment configuration used an Alpine Linux 3.24.2 VM with one vCPU, 256 MiB nominal memory (about 214.9 MiB guest MemTotal), 512 MiB swap, and swappiness 60. The runtime was OpenJDK 25.0.4 with -Xms16m -Xmx80m -XX:+UseSerialGC -Xss512k. StatLite 0.6.0, the monitor I develop at PVR Labs, polled at 30-second intervals. The workload lasted five minutes and scheduled 1,500 requests at five per second, with an 80/20 read/write mix and at most four outstanding requests. The MyBatis implementation and measurement record documents checks, inputs, and deviations.

There is one completed run per library. The measurements describe these applications and do not establish a statistically reliable ranking.

Jdbi Core implementation

The Jdbi variant uses Jdbi Core 3.55.0 with explicit Hikari, Jdbi, repository, and controller wiring. A plain QuoteRepository interface separates the controller from JdbiQuoteRepository. SQL and database-error translation stay in the persistence layer, with no DI container or extra service layer. Latest quotes use three queries on one handle; Jdbi constructs a query for each symbol where the raw JDBC baseline reused one prepared statement.

The full Jdbi results include acceptance checks, dependency measurements, and a comparison with the original JDBC application. In that comparison, Jdbi reached readiness 1.67 seconds later and used 6.41 MiB more workload RSS. Application restructuring also contributed to those differences, so they do not isolate Jdbi’s intrinsic overhead.

MyBatis Core implementation

The MyBatis variant uses MyBatis Core 3.5.19, an annotated mapper interface with visible SQL text blocks, an explicitly built SqlSessionFactory, and repository-owned session lifecycles. Its controller, repository interface, records, routes, H2/Hikari configuration, and portable error responses match the Jdbi application. Its first-level local cache is scoped to statements. Three-row writes use ExecutorType.BATCH, followed by an explicit flush and commit; preparation checks verified rollback when a later row conflicts.

jOOQ Open Source Edition implementation

The jOOQ Open Source Edition 3.21.9 application uses QuoteController → QuoteRepository → JooqQuoteRepository, a Hikari datasource, an H2 DSLContext, and generated quotes table and field types. The repository builds its lookups and inserts with jOOQ DSL expressions and maps results to the unchanged plain Java records. Request batches use a transaction-scoped DSL context and Batch.execute(); preparation confirmed rollback when a later row conflicts. A later correction also made fixture loading transactional and passed a separate host-side rollback/recovery check. That correction was not in the original VM run. Schema generation runs on the host from the same DDL resource used at startup, with generated classes separate from handwritten source.

Dependency and application footprint

The jOOQ shaded application JAR is about 18.3 MiB. Its additional runtime dependency set is jOOQ 3.21.9, r2dbc-spi 1.0.0.RELEASE, and reactive-streams 1.0.3. The latter two arrive transitively; the application uses JDBC. Code generation uses jooq-codegen-maven 3.21.9, its jooq-codegen and jooq-meta modules, and H2 2.4.240 in the Maven plugin realm, outside the measured application classpath. See the resolved runtime dependency tree, build-only artifact record, dependency verification, and code-cost record for artifact details.

The identical 83-line StatLite adapter is excluded from the primary comparison and recorded separately. These are counts, not maintainability scores.

Code generation and build complexity

The Maven generate-sources phase runs org.jooq:jooq-codegen-maven:3.21.9 against an in-memory H2 2.4.240 database initialized from src/main/resources/schema.sql. It generates only the QUOTES schema model under target/generated-sources/jooq. mvn -f javalin/sql-persistence-256mb/javalin-jooq/pom.xml clean package regenerates the model before compiling and shading the application. After a schema change, update the DDL resource, regenerate, inspect generated types, and rerun functional preparation. The generator runs on the host and its plugin dependencies do not enter the shaded runtime JAR.

Check jOOQ’s database support

Before choosing jOOQ, check whether its Open Source Edition supports your database and version. It supports databases such as H2, PostgreSQL, MySQL, MariaDB, and SQLite, but Oracle and SQL Server require a commercial edition. Older database versions may also require a commercial edition. See the edition list and version support matrix for your target database.

Limitations and conclusion

All three implementations completed the same workload with similar resident memory. The clearest differences were in paging, package size, and application code. Jdbi required the fewest handwritten Java lines here; MyBatis kept SQL in annotated mappers; jOOQ provided generated, typed schema references with an additional build step.

These are observations from one small, deterministic workload on a local VM, with one run per implementation. They do not isolate intrinsic library overhead or establish a performance ranking. The jOOQ figures describe the original measured build; the fixture-initialization correction was tested separately and remains unmeasured in the VM.
